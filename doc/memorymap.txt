This document outlines the basic code structure of the game, in case I forget
how everything works.

Memory map
==========

This defines the memory map of the game.  Formally, it tells the assember
where to place content in memory.  Currently I am using the simplest mapper,
NROM-128.  The linker configuration is in ``cfg/nrom128.cfg``.

The layout is simple::

   MEMORY {
       # RAM
        ZP: start=$0000, size=$0100, type=rw;
       RAM: start=$0200, size=$0600, type=rw;
   
       # ROM
       HDR: start=$0000, size=$0010, file=%O;
       PRG: start=$c000, size=$4000, file=%O, fill=yes, fillval=$ff;
   }
   
   SEGMENTS {
       # RAM
       ZEROPAGE: load=ZP,  type=zp;
            BSS: load=RAM, type=bss;
       # ROM
         HEADER: load=HDR, type=ro;
           CODE: load=PRG, type=ro;
         RODATA: load=PRG, type=ro;
        VECTORS: load=PRG, type=ro, start=$fffa;
   }


Memory
------

The Famicom's Ricoh 2A03 chip has 2kiB of on-chip memory.

The first 256 bytes ``[$0000:00ff]`` is identified as the "zero page" (ZP).
Instructions can reference the address of a zero page element using only one
byte, so they are generally smaller and the cycle counts are shorter.  For
example,

* ``lda $10`` requires three cycles, and
* ``lda $1234`` requires four cycles.

Sometimes the zero page elements are called "registers", but the memory itself
is no different from the rest of the on-chip memory.

The second region ``[$0200:$07ff]`` is the rest of the on-chip RAM, used for
general purpose computing when one can afford to use the longer instructions.

The region ``[$100:$1ff]`` is reserved for the internal "stack memory" for
operations such as function calls.  It can be used for storage, but there
is a risk of stack corruption.  For now, we simply exclude it from our linker
map.

All memory is tagged as ``rw``, indicating that can be used for reading and
writing.
